Что превращать в вектор: заголовок, текст, обрезка по длине и куски с заголовком статьи

Девять прошлых дорожок разбирали, что делать с векторами, когда они уже есть: гибридный поиск, пересортировка, разнообразие выдачи, сжатие, оценка поиска, фильтры, отказ при отсутствии ответа и сколько найденного отдавать модели. Сегодня шаг назад, к самому началу: какой именно текст мы подаём модели, чтобы получить вектор документа. Это решение принимают один раз при построении базы, и его почти никто не проверяет, хотя оно меняет качество поиска сильнее многих настроек после. Узкий вопрос дня: что кодировать — заголовок, текст, их склейку, обрезанное начало, куски с заголовком или несколько векторов сразу — и как это честно сравнить. Данные и модели те же, что в прошлые дни: набор SciFact из сборника BEIR (5183 научные аннотации с заголовками, 300 проверочных утверждений с размеченными правильными статьями) и векторы all-MiniLM-L6-v2 через ONNX Runtime на процессоре коробки. Все цифры ниже — из наших запусков; на других данных и моделях они будут другими, а способ проверки переносится как есть.

Все дорожки — /put. Прошлая — сколько найденного отдавать модели.

1 Какое поле превращать в вектор: заголовок, текст или оба одной строкой

Зачем это в работе. У любого документа в базе есть несколько полей: заголовок, основной текст, иногда аннотация, теги, имя раздела. Модель векторов (двойной кодировщик, bi-encoder — сеть, которая превращает каждый текст отдельно в список из нескольких сотен чисел так, что близкие по смыслу тексты получают близкие списки) принимает одну строку. Значит, кто-то решает, какую строку ей дать. Обычно склеивают «заголовок плюс текст» и не задумываются. Но заголовок — сжатая формулировка темы, а текст — подробности; вопрос пользователя может совпасть с любым из них. Пока вы не измерили поля по отдельности, вы не знаете, что именно находит ваш поиск и где он слепнет.

Как это устроено. Вектор документа у MiniLM получается так: текст режется на токены (кусочки слов), каждый токен проходит через шесть слоёв сети и получает свой вектор с учётом соседей, а потом все векторы токенов усредняются (усреднение по токенам, mean pooling) и делятся на свою длину, чтобы косинус можно было считать простым скалярным произведением. Важное следствие усреднения: каждый токен вносит примерно равную долю. В заголовке около двадцати токенов, в аннотации около трёхсот, поэтому в склейке «заголовок + текст» голос заголовка — примерно одна пятнадцатая. Он не пропадает, но тонет.

Есть три способа совместить поля. Первый — склеить в одну строку до кодирования: модель видит заголовок и текст вместе, внимание (attention) связывает слова из обоих, но длинный текст перевешивает. Второй — закодировать поля отдельно и сложить векторы: заголовок получает голос, равный тексту, но связи между полями внутри сети уже нет. Третий — держать два вектора и складывать не векторы, а оценки близости с весом; про него будет четвёртая ступень. Все три стоят по-разному: склейка — один вектор на документ, остальные — два.

Чтобы сравнивать честно, у каждого способа меряем одно и то же на одних вопросах: nDCG@10 (оценка порядка первой десятки, где правильная статья на первом месте весит больше, чем на десятом; от 0 до 1), полноту в первой десятке и в первой сотне. Дополнительно смотрим место первой правильной статьи по каждому вопросу: среднее прячет, что поля выигрывают на разных вопросах.

Отличие от соседнего понятия. Фильтр по метаданным (про него дорожка 20.11) использует поля как условие «пропустить или нет». Здесь поля становятся частью смысла: они влияют на сам вектор и, значит, на близость к вопросу.

Подробный пример. Общие модули lib.py, nlib.py и klib.py — те же, что в прошлые дни (обёртки моделей, загрузка SciFact, кэш векторов). Новое — flib.py: помощники для сравнения разных представлений документа, оценка статьи как лучшего из её кусков и подсчёт мест. Векторы полей мы посчитали один раз отдельным скриптом и сохранили: заголовки — за 9 секунд, тексты без заголовков — за 43 секунды на процессоре коробки.

# Добавления дорожки 23.11: что класть в вектор — поля, обрезка, куски с заголовком, слияние оценок.
from klib import *
import pickle
ids, texts, queries, qs, D, Q, rels = setup()
corpus, _, _ = load_scifact("test")
titles = [d["title"].strip() for d in corpus]; bodies = [d["text"].strip() for d in corpus]
N = len(texts)
def V(name): return np.load(f"{HERE}/{name}.npy")
RAWTOK = Tokenizer.from_file(f"{HERE}/models/bi/tokenizer.json"); RAWTOK.no_truncation(); RAWTOK.no_padding()
def ntok(xs): return np.array([len(e.ids) - 2 for e in RAWTOK.encode_batch(xs)])
def per_query(S):
    """S — матрица оценок (вопросы x статьи). Возвращает по каждому вопросу nDCG@10, recall@10, recall@100."""
    nd, r10, r100 = [], [], []
    for n in range(len(qs)):
        top = np.argpartition(-S[n], 100)[:100]; top = top[np.argsort(-S[n][top])]
        r = [int(i) for i in top]; rel = rels[n]
        nd.append(ndcg10(r, rel)); r10.append(recall(r, rel, 10)); r100.append(recall(r, rel, 100))
    return np.array(nd), np.array(r10), np.array(r100)
def summ(S):
    a, b, c = per_query(S); return a.mean(), b.mean(), c.mean()
def row(name, S, extra=""):
    a, b, c = summ(S); print(f"{name:44s} | nDCG@10 {a:.3f} | recall@10 {b*100:5.1f}% | recall@100 {c*100:5.1f}% {extra}")
def chunk_max(C, owner):
    """Оценка статьи = лучшая близость среди её кусков (max по кускам)."""
    S = np.full((len(qs), N), -np.inf, np.float32); P = Q @ C.T
    for n in range(len(qs)): np.maximum.at(S[n], owner, P[n])
    return S
def chunk_mean_vec(C, owner):
    """Один вектор на статью: среднее векторов её кусков, нормированное."""
    M = np.zeros((N, C.shape[1]), np.float32); np.add.at(M, owner, C)
    return M / np.linalg.norm(M, axis=1, keepdims=True)
def first_rel_rank(S, n):
    o = np.argsort(-S[n]); r = np.flatnonzero(np.isin(o, list(rels[n])))
    return int(r[0]) + 1 if len(r) else N
# Ступень 1. Какое поле превращать в вектор: заголовок, текст или оба.
from flib import *
Vt, Vb = V("V_title"), V("V_body")
tt, tb, tf = ntok(titles), ntok(bodies), ntok(texts)
print(f"статей {N}, вопросов {len(qs)}; токенов MiniLM: заголовок медиана {np.median(tt):.0f}, текст медиана {np.median(tb):.0f} (95-й перц. {np.percentile(tb,95):.0f}), заголовок+текст медиана {np.median(tf):.0f}")
print()
row("только заголовок", Q @ Vt.T)
row("только текст (без заголовка)", Q @ Vb.T)
row("заголовок + текст одной строкой", Q @ D.T)
avg = Vt + Vb; avg /= np.linalg.norm(avg, axis=1, keepdims=True)
row("среднее двух векторов (заголовок, текст)", Q @ avg.T)
# Насколько поля «смотрят в одну сторону»
cos_tb = np.sum(Vt * Vb, 1)
print(f"\nкосинус «заголовок ↔ текст» одной статьи: медиана {np.median(cos_tb):.3f}, 10-й перц. {np.percentile(cos_tb,10):.3f}, 90-й {np.percentile(cos_tb,90):.3f}")
st, sb, sf = Q @ Vt.T, Q @ Vb.T, Q @ D.T
rt = np.array([first_rel_rank(st, n) for n in range(len(qs))]); rb = np.array([first_rel_rank(sb, n) for n in range(len(qs))]); rf = np.array([first_rel_rank(sf, n) for n in range(len(qs))])
print(f"место первой правильной: заголовок лучше текста у {np.sum(rt<rb)} вопросов, хуже у {np.sum(rt>rb)}, поровну у {np.sum(rt==rb)}")
print(f"одной строкой лучше, чем лучшее из двух полей по отдельности, у {np.sum(rf<np.minimum(rt,rb))} вопросов; хуже лучшего поля у {np.sum(rf>np.minimum(rt,rb))}")
# пример: где заголовок сильно выигрывает и где проигрывает
d = rb - rt
ok = np.minimum(rt, rb) <= 10
for tag, n in [("заголовок выигрывает", int(np.argmax(np.where(ok, d, -10**9)))), ("заголовок проигрывает", int(np.argmin(np.where(ok, d, 10**9))))]:
    i = sorted(rels[n])[0]
    print(f"\n[{tag}] вопрос: «{queries[qs[n]]}»")
    print(f"  правильная статья — место по заголовку {rt[n]}, по тексту {rb[n]}, одной строкой {rf[n]}")
    print(f"  заголовок: {titles[i][:150]}")
    print(f"  начало текста: {bodies[i][:200]}")

Что видно. Склейка «заголовок + текст» лучше обоих полей по отдельности: nDCG@10 0,648 против 0,640 у одного текста и 0,564 у одного заголовка. Сложение двух отдельных векторов (0,632) хуже склейки: дав заголовку равный голос, мы его переоценили.

Но среднее скрывает главное. Заголовок ставит правильную статью выше текста у 79 вопросов, ниже — у 104. Пример с каналом TRPML показывает, где выигрывает заголовок: вопрос про ориентацию активатора в каналах hTRPML1 и hTRPML2, заголовок «Структуры канала TRPML1 человека» ставит статью на первое место, текст — на 206-е, склейка — на 128-е. Текст начинается с общего описания кальциевых каналов, и это описание перетягивает средний вектор. Обратный пример — подоциты: заголовок про методику прижизненной съёмки ставит статью на 1588-е место, текст, который прямо начинается словом «Podocytes», — на первое, склейка — на пятое.

Строка «одной строкой хуже лучшего поля у 102 вопросов» — это сравнение с подсказкой: «лучшее поле для этого вопроса» можно выбрать, только зная ответ. Такой потолок недостижим, но он показывает, сколько качества лежит в умении сочетать поля. Этим займёмся на четвёртой ступени.

Где обычно ошибаются.

  • Кодируют только заголовок «для скорости». У нас это стоит 0,084 nDCG@10 и шесть пунктов полноты в сотне. Заголовки короткие, но вопрос часто про деталь, которой в заголовке нет.
  • Кладут в склейку служебные поля — дату, номер, имя автора, разметку. Каждый такой токен получает голос в среднем векторе, а смысла вопроса не несёт.
  • Сравнивают способы по одному среднему и делают вывод «заголовок бесполезен». Он выигрывает у 79 вопросов из 300 — эту пользу можно забрать, если не выбрасывать поле, а правильно сочетать.

Словарь ступени.

Поле документа. Отдельная часть записи в базе: заголовок, текст, теги, раздел.

Двойной кодировщик (bi-encoder). Модель, которая кодирует вопрос и документ по отдельности в векторы и сравнивает их косинусом.

Усреднение по токенам (mean pooling). Способ получить один вектор текста: сложить векторы всех токенов и поделить на их число.

Склейка полей. Заголовок и текст подаются модели одной строкой, получается один вектор.

Сложение векторов полей. Каждое поле кодируется отдельно, векторы складываются и нормируются; поля получают равный голос.

nDCG@10. Оценка порядка первой десятки от 0 до 1: правильная статья наверху весит больше, чем внизу.

Оракул (oracle). Выбор, сделанный с подсказкой правильного ответа; показывает потолок, а не достижимый результат.

2 Обрезка по длине: что модель на самом деле видит из длинной статьи

Зачем это в работе. У любой модели векторов есть предел длины входа. Всё, что за ним, отбрасывается молча: ни ошибки, ни предупреждения, просто вектор описывает начало документа. Если ваши документы длиннее предела, часть базы для поиска невидима, и вопрос про последний абзац не найдёт свою статью никогда. Нужно знать три вещи: какой у модели предел, какая доля документов в него не влезает и есть ли в отрезанной части то, что спрашивают.

Как это устроено. Модель-трансформер различает порядок токенов через таблицу позиций: у каждой позиции свой выученный вектор. У MiniLM в файле настроек таблица рассчитана на 512 позиций, а в карточке модели указано, что тексты длиннее 256 токенов по умолчанию обрезаются. Длинные позиции модель видела в обучении редко или не видела вовсе, поэтому даже там, где таблица позволяет, качество на хвосте длинного текста не гарантировано. Это нужно проверять, а не предполагать.

Вторая причина ограничения — цена. Внимание сравнивает каждый токен с каждым, поэтому работа растёт примерно как квадрат длины. У нас кодирование всей базы при пределе 64 токена заняло 11 секунд, при 128 — 18, при 512 — 137: предел вырос в четыре раза (со 128 до 512), а время — в 7,6 раза. Замеры грубые, по одному запуску, но порядок виден.

Третья тонкость — обрезка меняет не только длинные документы. Вектор короткой статьи от предела не зависит, но её место в выдаче зависит от соседей, а векторы длинных соседей изменились. Поэтому эффект обрезки надо мерить по всей выдаче, а не только на длинных документах.

Отличие от соседнего понятия. Окно контекста языковой модели (про него дорожка 09.10) ограничивает, сколько текста модель прочитает при ответе. Предел модели векторов — другой и обычно намного меньше: он ограничивает, сколько текста попадёт в один вектор при поиске. Документ может спокойно влезать в окно ответа и при этом быть обрезан при поиске.

Подробный пример. Кодируем склейку «заголовок + текст» с пределами 64, 128, 256 и 512 токенов (вариант 256 — тот, что был у нас все прошлые дни) и сравниваем выдачу. Затем берём куски по три предложения, которые мы нарезали в дорожке 21.11, находим для каждой пары «вопрос — правильная статья» кусок, самый близкий к вопросу, и смотрим, с какого токена статьи он начинается.

# Ступень 2. Обрезка по длине: что модель на самом деле видит из длинной статьи.
from flib import *
tf = ntok(texts)
for L in [64, 128, 256, 512]: print(f"длиннее {L} токенов: {np.mean(tf>L)*100:5.1f}% статей")
print()
res = {}
for L, name in [(64,"V_full64"),(128,"V_full128"),(256,None),(512,"V_full512")]:
    X = D if name is None else V(name); S = Q @ X.T; res[L] = per_query(S)
    print(f"обрезка {L:3d} токенов | nDCG@10 {res[L][0].mean():.3f} | recall@10 {res[L][1].mean()*100:5.1f}% | recall@100 {res[L][2].mean()*100:5.1f}%")
# вопросы, у которых правильная статья длинная
longq = np.array([any(tf[i] > 256 for i in rels[n]) for n in range(len(qs))])
print(f"\nвопросов, где хотя бы одна правильная статья длиннее 256 токенов: {longq.sum()} из {len(qs)}")
for L in [128, 256, 512]:
    print(f"  обрезка {L}: nDCG@10 на «длинных» {res[L][0][longq].mean():.3f}, на остальных {res[L][0][~longq].mean():.3f}")
# где внутри правильной статьи лежит кусок, ближе всего похожий на вопрос
z = np.load(f"{HERE}/chunks.npz"); C, owner = z["C"], z["owner"]
ch = pickle.load(open(f"{HERE}/chunk_texts.pkl","rb"))["plain"]
start = {}; pos_tok = np.zeros(len(ch), int)
for j in range(len(ch)):
    i = owner[j]
    if i not in start: start[i] = 0
    pos_tok[j] = start[i]; start[i] += len(RAWTOK.encode(ch[j]).ids) - 2
beyond = []; total = 0
for n in range(len(qs)):
    for i in rels[n]:
        js = np.flatnonzero(owner == i); b = js[np.argmax(C[js] @ Q[n])]; total += 1
        beyond.append(pos_tok[b] >= 256)

Что видно. Предел 256 токенов не вмещает 70,8% статей SciFact целиком, а 512 — только 8,7%. Самый короткий предел бьёт сильно: при 64 токенах (примерно заголовок и одна-две фразы) nDCG@10 падает до 0,575, при 128 — до 0,622. Переход с 256 на 512 даёт 0,653 вместо 0,648 и полноту в сотне 93,5% вместо 92,5%: небольшая прибавка, при том что время кодирования базы выросло многократно.

Почему прибавка мала, объясняет последняя строка: самый похожий на вопрос кусок начинается после 256-го токена только в 43 парах из 339 (12,7%). В научных аннотациях главное обычно в начале — тема, цель, основной результат. В договорах, инструкциях или протоколах встреч всё может быть наоборот, и там та же проверка покажет другое.

Обратите внимание на вопросы, у которых все правильные статьи короткие (76 вопросов): их nDCG@10 при переходе с 256 на 512 вырос с 0,631 до 0,646, хотя векторы самих правильных статей не изменились. Это эффект соседей из третьего абзаца: длинные посторонние статьи получили другие векторы и иначе встали в выдаче.

Где обычно ошибаются.

  • Не знают предел своей модели и считают, что документ «весь в векторе». Проверьте настройку токенизатора и посчитайте долю документов длиннее предела, как в первых строках примера.
  • Поднимают предел до максимума таблицы позиций и ждут большого выигрыша. У нас 256→512 дало +0,005 nDCG@10 ценой многократного роста времени; куски на следующей ступени дали в несколько раз больше.
  • Мерят эффект обрезки только на длинных документах и пропускают сдвиг выдачи для коротких.

Словарь ступени.

Предел длины входа (max sequence length). Сколько токенов модель векторов принимает; остальное отбрасывается.

Обрезка (truncation). Молчаливое отбрасывание токенов после предела при кодировании.

Таблица позиций (position embeddings). Выученные векторы, по которым модель различает, на каком месте стоит токен.

Квадратичная цена внимания. Работа внимания растёт примерно как квадрат длины текста, потому что каждый токен сравнивается с каждым.

Карточка модели (model card). Описание модели от её авторов: на чём обучена, какие у неё пределы и настройки по умолчанию.

Эффект соседей. Место документа в выдаче зависит от векторов всех остальных документов, поэтому изменение одних сдвигает другие.

3 Куски с заголовком: приставка, которая возвращает куску тему статьи

Зачем это в работе. Обрезку обходят нарезкой: длинный документ режут на куски, каждый кодируют отдельно, а оценкой документа считают лучшую близость среди его кусков. Но кусок из середины часто не понимает, о чём он: «Медианное наблюдение — 6,3 года, частота рецидивов 14,9%» — рецидивов чего, при каком лечении? Тема была в заголовке, а заголовок остался в первом куске. Простое лекарство — приставить к каждому куску заголовок документа (контекстная приставка, contextual chunk header). Это стоит денег и места, поэтому нужно измерить, окупается ли.

Как это устроено. Нарезку мы взяли из дорожки 21.11: по три предложения подряд, без перекрытия; про выбор размера кусков была дорожка 16.10. Склейка «заголовок. текст» при нарезке даёт заголовок только первому куску статьи. Во втором варианте к каждому следующему куску спереди добавлен тот же заголовок. Оценка статьи в обоих вариантах — максимум близости по её кускам (max по кускам, max-pooling): статья хороша, если хорош хотя бы один её кусок.

Почему приставка помогает. Вектор куска — среднее по его токенам. Заголовок добавляет токены темы, и вектор куска сдвигается к теме статьи. Вопрос, который упоминает и тему, и деталь, теперь совпадает с куском по обоим признакам. Цена — длина: каждый кусок становится длиннее на заголовок, а значит, кодирование дороже, и если кусок с приставкой близок к пределу длины, приставка может вытеснить его хвост.

Ограничение приставки — она одна на всю статью. Если заголовок общий («Отчёт за третий квартал»), он не помогает, а все куски документа становятся похожи друг на друга. Более дорогие варианты — краткая выжимка документа или описание места куска, сгенерированные языковой моделью для каждого куска, — мы сегодня не проверяли.

Отличие от соседнего понятия. Перекрытие кусков (overlap) повторяет соседний текст на границе, чтобы не разрезать мысль пополам. Приставка повторяет не соседний текст, а общий контекст документа, одинаковый для всех его кусков. Это разные лекарства от разных болезней, и их можно сочетать.

Подробный пример. Сравниваем четыре представления: один вектор на статью (как раньше), куски без приставки, куски с приставкой и, для сравнения, один вектор на статью как среднее векторов кусков с приставкой. Векторы кусков с приставкой (19 550 штук) посчитаны один раз за 157 секунд.

# пример: кусок, который без заголовка непонятен

print(f"место первой правильной: с приставкой лучше у {np.sum(rq<rp)} вопросов, хуже у {np.sum(rq>rp)}, поровну у {np.sum(rq==rp)}")
def bestchunk(n):
    i = sorted(rels[n])[0]; js = np.flatnonzero(owner == i); return i, js, js[np.argmax(Cp[js] @ Q[n])]
cand = [n for n in range(len(qs)) if rq[n] <= 3 and not first[bestchunk(n)[2]]]
cand = [n for n in cand if rp[n] > rq[n]]
n = max(cand, key=lambda n: (Cp[bestchunk(n)[2]] - C[bestchunk(n)[2]]) @ Q[n]); i, js, b = bestchunk(n)
print(f"\nпример: «{queries[qs[n]]}»")
print(f"  место правильной статьи: без приставки {rp[n]}, с приставкой {rq[n]}")
print(f"  лучший кусок (№{b-js[0]+1} из {len(js)}), близость без приставки {C[b]@Q[n]:.3f}, с приставкой {Cp[b]@Q[n]:.3f}")
print(f"  заголовок: {titles[i][:160]}")
print(f"  текст куска: {T['plain'][b][:300]}")

Где обычно ошибаются.

  • Усредняют векторы кусков в один «для экономии» и удивляются, что нарезка ничего не дала. У нас среднее вернуло качество к уровню одного вектора на статью.
  • Добавляют приставку, не проверив длину: длинный заголовок плюс длинный кусок могут перейти предел модели, и тогда обрезается уже сам текст куска.

Словарь ступени.

Кусок (chunk). Часть документа, которая кодируется в отдельный вектор.

Контекстная приставка (contextual chunk header). Заголовок или описание документа, добавленные в начало каждого куска перед кодированием.

Max по кускам (max-pooling). Оценка документа равна лучшей близости среди его кусков.

Средний вектор кусков. Один вектор на документ, полученный усреднением векторов кусков; теряет точность лучшего куска.

Перекрытие кусков (overlap). Повтор нескольких предложений на границе соседних кусков, чтобы не разрывать мысль.

Нарезка по предложениям. Куски из фиксированного числа предложений подряд, у нас по три.

4 Несколько векторов на статью: как слить оценки полей и кусков

Зачем это в работе. Первая ступень показала, что заголовок и текст выигрывают на разных вопросах, третья — что куски и целая статья ловят разное. Естественная мысль — хранить несколько векторов на документ и объединять их оценки. Это часто делают в рабочих системах, но у слияния есть настройка — вес каждого источника, — и от неё зависит, будет ли выигрыш вообще. Плюс каждый лишний вектор — это память и время поиска.

Как это устроено. Самый простой способ — взвешенная сумма близостей: оценка = a × близость к заголовку + (1 − a) × близость к тексту. Здесь оба числа — косинусы одной и той же модели, поэтому шкалы сопоставимы и сумма имеет смысл. Если бы мы складывали косинус и оценку BM25 (оценку по совпадению слов), шкалы были бы разными, и вес пришлось бы подбирать заново при любой смене данных.

Второй способ — слияние по местам (RRF, reciprocal rank fusion): каждый источник даёт документу 1 / (60 + место), очки складываются. Шкалы оценок не важны, важен только порядок. Мы уже применяли его в дорожке про гибридный поиск. Его слабость — он выбрасывает информацию о том, насколько первый документ оторвался от второго, и одинаково слушает и сильный, и слабый источник.

Третий способ мы сделали на прошлой ступени, не называя: max по кускам — тоже слияние, только по правилу «слушаем самый уверенный вектор». Разница с суммой важна: максимум награждает документ за один очень похожий кусок, сумма — за общую похожесть со всех сторон.

Цена в памяти простая и линейная: каждый вектор MiniLM — 384 числа по 4 байта. Один вектор на статью для нашей базы — 7,6 МиБ, статья плюс куски — 36,2 МиБ. На миллионе документов это уже разница между гигабайтом и пятью, а сжатие из дорожки 18.11 уменьшает обе цифры одинаково.

Подробный пример. Перебираем вес a для заголовка и текста, вес b для целой статьи и лучшего куска с приставкой, и пробуем RRF двух и трёх источников. Обратите внимание: здесь веса подбираются на тех же 300 вопросах, на которых меряем. Это сознательная ошибка, которую исправит пятая ступень.

# Ступень 4. Несколько векторов на статью и слияние оценок.
from flib import *
z = np.load(f"{HERE}/chunks.npz"); owner = z["owner"]; Cp = V("C_pref")
St, Sb, Sf = Q @ V("V_title").T, Q @ V("V_body").T, Q @ D.T
Sq = chunk_max(Cp, owner)
print("взвешенная сумма близостей: a·заголовок + (1−a)·текст")
for a in [0, .1, .2, .3, .4, .5, .7, 1]:
    row(f"  a = {a:.1f}", a * St + (1 - a) * Sb)
print()
print("целая статья + лучший кусок с заголовком: b·статья + (1−b)·кусок")
for b in [0, .3, .5, .7, 1]:
    row(f"  b = {b:.1f}", b * Sf + (1 - b) * Sq)
def rrf(*Ss, k=60):
    out = np.zeros_like(Ss[0])
    for S in Ss:
        r = np.argsort(np.argsort(-S, axis=1), axis=1)
        out += 1.0 / (k + r + 1)
    return out
row("слияние по местам (RRF, k=60): статья + куски", rrf(Sf, Sq))
row("RRF: заголовок + текст + куски", rrf(St, Sb, Sq))
print()
nv = {"один вектор на статью": N, "заголовок + текст": 2*N, "куски": len(owner), "статья + куски": N+len(owner)}
for k, v in nv.items(): print(f"{k:24s}: {v:6d} векторов, {v*384*4/2**20:5.1f} МиБ в float32")

  b = 0.5                                    | nDCG@10 0.675 | recall@10  80.4% | recall@100  94.8% 
  b = 0.7                                    | nDCG@10 0.662 | recall@10  79.8% | recall@100  94.5% 
  b = 1.0                                    | nDCG@10 0.648 | recall@10  78.8% | recall@100  92.5% 
слияние по местам (RRF, k=60): статья + куски | nDCG@10 0.675 | recall@10  80.3% | recall@100  95.2% 
RRF: заголовок + текст + куски               | nDCG@10 0.629 | recall@10  76.4% | recall@100  94.9% 

один вектор на статью   :   5183 векторов,   7.6 МиБ в float32
заголовок + текст       :  10366 векторов,  15.2 МиБ в float32
куски                   :  19550 векторов,  28.6 МиБ в float32
статья + куски          :  24733 векторов,  36.2 МиБ в float32

Что видно. Взвешенная сумма заголовка и текста почти не обгоняет простую склейку: лучший a = 0,2 даёт 0,650 против 0,648. Хранить два вектора ради этого не стоит; склейка делает то же самое бесплатно. При a выше 0,4 качество падает, при a = 1 (только заголовок) — 0,564.

Целая статья плюс лучший кусок с приставкой дают b = 0,3: nDCG@10 0,687 и лучшая за сегодня полнота в сотне — 95,1%. Но по nDCG@10 это почти то же, что одни куски (0,686), а вектор целой статьи добавляет 7,6 МиБ. Выигрыш в сотне полезен, если дальше стоит пересортировка, которая берёт именно сотню кандидатов.

RRF двух источников (0,675) хуже взвешенной суммы и хуже одних кусков: равный голос слабому источнику тянет вниз. RRF трёх источников, где один из них — слабый заголовок, падает до 0,629, то есть ниже, чем один вектор на статью. Хорошая иллюстрация: добавить источник в слияние по местам — не бесплатно, если источник слабый.

Где обычно ошибаются.

  • Складывают оценки разных шкал (косинус и BM25) с весом 0,5 «поровну». Поровну по весу не значит поровну по влиянию; сначала приведите шкалы к одному виду или используйте места.
  • Добавляют в RRF все источники подряд. У нас третий слабый источник опустил качество ниже исходного.
  • Подбирают вес на тех же вопросах, на которых потом отчитываются. Цифры этой ступени оптимистичны — насколько, покажет следующая.

Словарь ступени.

Слияние оценок (score fusion). Объединение оценок нескольких источников в одну оценку документа.

Взвешенная сумма близостей. Оценка = вес × близость первого источника + (1 − вес) × близость второго.

RRF (reciprocal rank fusion). Слияние по местам: каждый источник даёт документу 1 / (60 + место), очки складываются.

Шкала оценок. Диапазон и смысл чисел, которые выдаёт источник; у косинуса и BM25 они разные.

Несколько векторов на документ (multi-vector). Документ хранится как набор векторов — полей или кусков, — а оценки сливаются при поиске.

МиБ (мебибайт). 2 в 20-й степени байт, около 1,05 миллиона байт.

Полнота в сотне (recall@100). Доля правильных статей, попавших в первые сто; важна, если дальше стоит пересортировка сотни.

5 Где выбор ломается: подгонка веса, шум и тяга к статьям с множеством кусков

Зачем это в работе. Выбор представления документа кажется техническим, но на нём легко обмануть себя: подобрать вес на тех же вопросах, принять шум за выигрыш или не заметить, что новый способ систематически предпочитает определённый тип документов. Перед тем как перестраивать базу (а это часы кодирования и миграция индекса), нужно ответить на три вопроса: переносится ли выигрыш на новые вопросы, не случайный ли он и не появился ли перекос.

Как это устроено. Против подгонки — разделение вопросов: делим 300 вопросов пополам случайно, вес выбираем на одной половине, меряем на другой, и повторяем 20 раз с разным делением. Разница между приростом на половине подбора и на проверочной — это и есть оптимизм от подгонки. Против шума — бутстрэп по вопросам (про него подробно дорожка 19.11): 2000 раз пересобираем набор вопросов с возвращением и смотрим, в каком диапазоне лежит средний прирост.

Против перекоса — проверка того, кого выбирает новый способ. Max по кускам даёт статье тем больше шансов, чем больше у неё кусков: у каждого куска своя случайная ошибка близости, и максимум из пяти случайных величин в среднем выше максимума из двух. Значит, длинные статьи могут подниматься не потому, что они лучше отвечают, а потому, что у них больше лотерейных билетов. Проверяем это, сравнивая долю статей с разным числом кусков в базе и в первой десятке.

Отличие от соседнего понятия. На прошлой дорожке мы видели тягу перекрёстного кодировщика к длинным статьям — то было свойство модели пересортировки. Здесь похожий перекос рождается не моделью, а правилом сборки оценки (максимумом), и лечится тоже правилом: например, сравнением с целой статьёй через вес b.

Подробный пример. Берём лучшую схему четвёртой ступени — целая статья плюс лучший кусок с приставкой — и проверяем её тремя способами.

# Ступень 5. Где выбор ломается: подгонка веса на тех же вопросах, шум, проигравшие вопросы.
from flib import *
z = np.load(f"{HERE}/chunks.npz"); owner = z["owner"]; Cp = V("C_pref")
St, Sb, Sf = Q @ V("V_title").T, Q @ V("V_body").T, Q @ D.T
Sq = chunk_max(Cp, owner)
grid = np.round(np.arange(0, 1.01, 0.1), 1)
cache = {b: per_query(b * Sf + (1 - b) * Sq)[0] for b in grid}
base = per_query(Sf)[0]
best_all = max(grid, key=lambda b: cache[b].mean())
print(f"лучший вес b на всех 300 вопросах: {best_all}, nDCG@10 {cache[best_all].mean():.3f} (база — целая статья {base.mean():.3f})")
gains = []
for seed in range(20):
    A, B = split_by_query(len(qs), seed); A, B = sorted(A), sorted(B)
    b = max(grid, key=lambda b: cache[b][A].mean())
    gains.append((b, cache[b][A].mean() - base[A].mean(), cache[b][B].mean() - base[B].mean()))
g = np.array(gains)
print(f"20 случайных делений вопросов пополам: вес подбираем на одной половине, проверяем на другой")
print(f"  выбранный b: от {g[:,0].min()} до {g[:,0].max()}; прирост на половине подбора в среднем {g[:,1].mean():+.3f}, на проверочной {g[:,2].mean():+.3f} (от {g[:,2].min():+.3f} до {g[:,2].max():+.3f})")
d = cache[best_all] - base
rng = np.random.default_rng(0); bs = [d[rng.integers(0, len(d), len(d))].mean() for _ in range(2000)]
print(f"прирост лучшего b против базы: {d.mean():+.3f}, 95% интервал бутстрепа по вопросам [{np.percentile(bs,2.5):+.3f}; {np.percentile(bs,97.5):+.3f}]")
print(f"  вопросов стало лучше {np.sum(d>1e-9)}, хуже {np.sum(d<-1e-9)}, без изменений {np.sum(np.abs(d)<=1e-9)}")
dq = per_query(Sq)[0] - base
print(f"куски с заголовком против целой статьи: лучше у {np.sum(dq>1e-9)}, хуже у {np.sum(dq<-1e-9)}, без изменений {np.sum(np.abs(dq)<=1e-9)}; средний сдвиг {dq.mean():+.3f}")
# тяга к статьям с большим числом кусков: у кого больше кусков — больше шансов на случайно высокий максимум
nch = np.bincount(owner, minlength=N)
top_full = np.concatenate([np.argsort(-Sf[n])[:10] for n in range(len(qs))])
top_q = np.concatenate([np.argsort(-Sq[n])[:10] for n in range(len(qs))])
relall = np.array(sorted({i for r in rels for i in r}))
print(f"\nсреднее число кусков: у всех статей {nch.mean():.2f}, у правильных {nch[relall].mean():.2f}, в первой десятке целой статьи {nch[top_full].mean():.2f}, в первой десятке «лучшего куска» {nch[top_q].mean():.2f}")
for lo, hi in [(1,2),(3,4),(5,7),(8,100)]:
    m = (nch >= lo) & (nch <= hi)
    print(f"  статьи с {lo}–{hi} кусками: доля в базе {m.mean()*100:5.1f}%, доля в первой десятке: целая статья {np.isin(top_full, np.flatnonzero(m)).mean()*100:5.1f}%, лучший кусок {np.isin(top_q, np.flatnonzero(m)).mean()*100:5.1f}%")

Что видно. Подгонка завышает результат, но не уничтожает его: при подборе на половине прирост к целой статье в среднем +0,043, на проверочной половине — +0,033, и во всех 20 делениях он остался положительным (от +0,020 до +0,051). Выбранный вес гуляет от 0 до 0,3: значит, точное значение b не важно, важно, что кусков слушаем больше, чем статью. Бутстрэп даёт для прироста интервал от +0,021 до +0,058 — ноль в него не входит. По вопросам: стало лучше у 60, хуже у 24, у 216 без изменений. Выигрыш реальный, но сосредоточен примерно на пятой части вопросов, а у каждого двенадцатого стало хуже.

Перекос есть, но небольшой. В первой десятке «лучшего куска» статьи в среднем состоят из 4,47 кусков против 3,77 во всей базе и 3,73 у правильных статей. Статьи с 5–7 кусками занимают 19,2% базы и 21,3% первой десятки, статьи с 1–2 кусками — 15,5% базы и только 13,1% десятки. У целой статьи этот сдвиг слабее (4,05). Для SciFact, где длины ровные, это терпимо. В базе, где рядом лежат записки на абзац и руководства на сто страниц, тот же механизм может вытолкнуть короткие документы из выдачи, и это надо мерить на своих данных.

Где обычно ошибаются.

  • Отчитываются цифрой, на которой подбирали вес. У нас разница между подбором и проверкой — около 0,01 nDCG@10, на меньших наборах вопросов она бывает больше самого выигрыша.
  • Смотрят только на средний прирост и не считают проигравшие вопросы. 24 вопроса из 300 стали хуже — их стоит открыть глазами до перестройки базы.
  • Не проверяют, кого выбирает максимум по кускам. Длинные документы получают больше шансов просто из-за числа кусков.

Словарь ступени.

Подгонка на испытательном наборе. Выбор настройки на тех же вопросах, на которых меряют качество; даёт завышенную оценку.

Разделение вопросов пополам (split). Одна половина для подбора настройки, другая для честной проверки.

Бутстрэп по вопросам (bootstrap). Многократная пересборка набора вопросов с возвращением, чтобы увидеть разброс среднего.

95% интервал. Диапазон, в который попали 95% пересобранных средних; если ноль вне его, выигрыш вряд ли случаен.

Перекос по длине (length bias). Систематическое предпочтение длинных или коротких документов, не связанное с их полезностью.

Эффект числа билетов. Максимум из большего числа случайных величин в среднем выше, поэтому документы с многими кусками получают лишний шанс.

Миграция индекса. Перестройка базы векторов под новое представление документов: перекодирование и замена старого индекса.
