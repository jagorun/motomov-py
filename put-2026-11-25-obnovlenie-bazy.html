Как обновлять поисковую базу, не ломая поиск: добавление, удаление, новые версии и смена модели векторов

Прошлые дорожки строили поиск по неподвижной базе: гибридный поиск, сжатие векторов, оценка поиска, фильтры по метаданным, что превращать в вектор, опечатки в вопросе. В работе база живёт: статьи добавляют, удаляют, правят, а однажды меняют и саму модель векторов. Узкий вопрос дня: что именно ломается в поиске при каждом из этих изменений и как обновлять базу так, чтобы качество не падало молча. Данные те же, что в прошлые дни: SciFact из сборника BEIR (5183 научные аннотации, 300 проверочных утверждений с размеченными правильными статьями), векторы all-MiniLM-L6-v2 через ONNX Runtime на процессоре коробки, словесный поиск BM25 на numpy. Добавления, удаления и правки мы изображаем сами, случайным выбором статей с зерном, поэтому это испытание, а не журнал настоящей базы. Все цифры ниже — из наших запусков; на других данных они будут другими, а способ проверки переносится как есть.

Все дорожки — /put. Прошлая — опечатки в вопросе.

1 Добавили статьи: что пересчитывать в BM25 и что в векторах

Зачем это в работе. Новые документы приходят каждый день, и пересобирать весь индекс (структуру, по которой поиск быстро находит статьи) на каждую новую статью дорого. Поэтому первое, что надо понимать: какая часть индекса зависит только от самой статьи, а какая — от всей базы сразу. То, что зависит от одной статьи, можно досчитать и дописать. То, что зависит от всей базы, со временем устаревает, и если про это забыть, поиск начинает ранжировать по вчерашней картине мира.

Как это устроено. Вектор статьи в нашем поиске считается из текста одной этой статьи: модель читает её токены (кусочки слов), усредняет их скрытые состояния и нормирует результат до длины 1. Соседи по базе в расчёт не входят. Значит, при добавлении достаточно посчитать векторы новых статей той же моделью тем же способом и дописать их в индекс. Старые векторы трогать не нужно. Мы это проверили: вектор статьи, посчитанный поодиночке, совпал с вектором той же статьи в пакете из 64 и с вектором, лежащим в индексе, до последнего знака.

BM25 устроен иначе. Вес слова в нём зависит от общей статистики базы: сколько статей всего (N), в скольких из них встречается слово (документная частота, df) и какова средняя длина статьи. Редкое слово получает большой вес обратной частоты (IDF), частое — маленький. Когда в базу приходят новые статьи, все три числа меняются, и веса всех слов в принципе надо пересчитать. Многие системы делают это сами при слиянии сегментов индекса, но самодельный индекс или словарь, «обученный» один раз (например, TfidfVectorizer из scikit-learn после fit), так не умеет.

Есть два разных вида устаревания. Первый — числа N, df и средняя длина посчитаны по старой части базы, а слова новых статей в индекс всё же попадают. Второй, опаснее, — заморожен сам словарь: слово, которого не было при первой сборке, выбрасывается и из новых статей, и из вопросов. Первый вид сдвигает веса, второй делает новые термины невидимыми. В научной базе новые термины — это новые вещества, гены и дозировки, то есть ровно то, что люди ищут.

Отличие от соседнего понятия: здесь речь не о дообучении модели векторов. Модель не меняется, меняется только набор статей. Если же вы меняете модель, это совсем другая история — смешение двух пространств, о нём ступень 4.

Пример. Изображаем «первую сборку» на 90%, 50% и 20% базы (по три случайных выбора с зернами 0, 1, 2), затем кладём в индекс все 5183 статьи, но статистику оставляем старой. Сравниваем с полной пересборкой. Класс StatBM25 умеет считать статистику по одному набору статей, а индексировать другой.

# Добавления для дорожки 25.11: BM25, у которого статистика базы (N, df, средняя длина) может быть «заморожена»
# на старой части базы, и оценка по списку номеров с повторами.
from nlib import *
from tlib import terms

class StatBM25:
    """BM25 по словам. stats_docs — документы, по которым считали N, df и среднюю длину (как при первой сборке индекса).
    index_docs — документы, которые реально лежат в индексе. freeze_vocab=True: слова, которых не было в stats_docs,
    выбрасываются из документов и вопросов (так работает словарь, «обученный» один раз)."""
    def __init__(self, index_docs, stats_docs=None, k1=1.2, b=0.75, freeze_vocab=False):
        stats_docs = index_docs if stats_docs is None else stats_docs
        self.N = len(stats_docs); df = Counter()
        for d in stats_docs: df.update(set(d))
        self.avg = np.mean([len(d) for d in stats_docs]); self.df = df; self.fz = freeze_vocab
        self.k1, self.b = k1, b; self.n = len(index_docs)
        self.post = defaultdict(lambda: ([], []))
        for i, d in enumerate(index_docs):
            L = len(d)
            for w, c in Counter(d).items():
                if freeze_vocab and w not in df: continue
                a, v = self.post[w]; a.append(i); v.append((c, L))
        self.P = {}
        for w, (a, v) in self.post.items():
            n = df.get(w, 0)
            idf = math.log(1 + (self.N - n + 0.5) / (n + 0.5))
            c = np.array([x[0] for x in v], float); L = np.array([x[1] for x in v], float)
            self.P[w] = (np.array(a), (idf * c * (k1 + 1) / (c + k1 * (1 - b + b * L / self.avg))).astype(np.float32))
    def scores(self, q_terms):
        s = np.zeros(self.n, np.float32)
        for w in set(q_terms):
            if w in self.P: a, v = self.P[w]; s[a] += v
        return s

def ndcg_ids(order_ids, rel):
    """nDCG@10 по списку идентификаторов, где один и тот же id может повторяться: повтор правильного не считается."""
    seen, dcg = set(), 0.0
    for r, d in enumerate(order_ids[:10]):
        if d in rel and d not in seen: dcg += 1 / math.log2(r + 2)
        seen.add(d)
    return dcg / sum(1 / math.log2(r + 2) for r in range(min(len(rel), 10)))

def ndcg_rows(S, rels, k=10):
    """Средний nDCG@10 по матрице оценок S (вопросы × статьи)."""
    out = []
    for n, rel in enumerate(rels):
        o = np.argpartition(-S[n], k)[:k]; o = o[np.argsort(-S[n][o])]
        out.append(ndcg_ids(o.tolist(), rel))
    return float(np.mean(out))

Что видно. Пока словарь открыт, устаревшие N, df и средняя длина почти не вредят: даже статистика от 20% базы дала 0,662 против 0,663 у пересборки. На случайной выборке частоты слов в части базы похожи на частоты во всей базе. Заморозка словаря — другое дело: при словаре от 50% базы из вопросов выпадает 6,3% слов, задето 126 вопросов из 300, и nDCG@10 падает до 0,630, а при словаре от 20% — до 0,578. Выпадают как раз «400mg», «albendazole», «aldh1». Важная оговорка: у нас новые статьи — случайная часть той же базы. Если новые статьи про новую тему, сдвиг частот будет сильнее, и это надо мерить на своих данных.

Где обычно ошибаются.

  • Пересчитывают векторы всех статей при каждом добавлении. Это не нужно, пока модель и способ подготовки текста те же: вектор статьи не зависит от соседей.
  • Используют словарь или векторизатор, обученный один раз, и не замечают, что новые слова молча выбрасываются. Ошибки нет, просто поиск по новым терминам ничего не находит.
  • Пересобирают статистику BM25 по расписанию «когда-нибудь» и не проверяют, насколько новые статьи отличаются по словам от старых. Случайная добавка безопасна, тематический сдвиг — нет.

Словарь ступени.

Индекс. Заранее подготовленная структура, по которой поиск быстро находит статьи; для векторов это сами векторы, для BM25 — списки «слово → статьи».

Документная частота (df). В скольких статьях базы встречается слово хотя бы раз.

Обратная частота (IDF). Вес слова, который тем больше, чем реже слово в базе; у BM25 считается из N и df.

Статистика базы. Числа, которые BM25 берёт со всей базы сразу: число статей, частоты слов и средняя длина статьи.

Замороженный словарь. Набор слов, зафиксированный при первой сборке; слов вне него поиск не видит.

Сегмент индекса (segment). Кусок индекса, который дописали отдельно; поисковые движки потом сливают сегменты и пересчитывают статистику.

Пересборка (rebuild). Построение индекса заново по всем текущим статьям.

Дописывание (incremental add). Добавление новых статей в готовый индекс без пересчёта старых.

2 Удалили статьи: метки удаления и почему выдача пустеет

Зачем это в работе. Документы удаляют по разным причинам: устарели, отозваны, пользователь потребовал стереть свои данные, у человека пропал доступ. Удалённая статья не должна попасть ни в выдачу, ни в ответ модели. При этом физически вычистить её из индекса сразу часто нельзя или дорого, и многие системы сначала только помечают её. Если фильтр по меткам стоит не там, пользователь получает вместо десяти результатов пять, а модель — половину нужного контекста.

Как это устроено. Метка удаления (tombstone) — отметка «эта статья удалена», которая лежит рядом с индексом. Сама статья и её вектор остаются на месте до уборки (compaction — пересборки сегментов без помеченных записей). Поиск должен на каждом запросе не отдавать помеченное. Вопрос только в том, где он это делает: до выбора первой десятки или после.

Фильтр после поиска (post-filter) берёт k лучших кандидатов и выкидывает из них удалённые. Если удалённых в базе много, среди k лучших их тоже много, и до десяти уже не набирается. Фильтр внутри поиска (pre-filter, или фильтр во время обхода индекса) исключает удалённые до того, как выбрана десятка; тогда выдача всегда полная, если живых статей хватает. Это та же развилка, что в дорожке про фильтры по метаданным, только фильтр здесь — «не удалено».

Простое средство для фильтра после поиска — брать кандидатов с запасом (over-fetch): не 10, а 20 или 40. Запас должен расти с долей удалённых: при доле d в среднем на k кандидатов приходится k·(1−d) живых, и для надёжной десятки нужен запас сверх этого среднего, потому что удалённые ложатся в первые места неравномерно.

Для BM25 у удаления есть вторая сторона: помеченные статьи пока ещё сидят в статистике базы. N, df и средняя длина считают и мёртвые статьи. После уборки статистика пересчитывается.

Пример. Удаляем 10%, 30%, 50% и 70% статей случайно (зерно 0). Чтобы не путать два эффекта, удаляем только статьи, которые не являются правильными ни для одного вопроса: в SciFact правильных таких 283 из 5183. Смотрим, сколько результатов остаётся в десятке при фильтре после поиска с запасом 10, 20 и 40, и сравниваем с фильтром внутри поиска. Затем для BM25 сравниваем статистику с мёртвыми статьями и пересчитанную.

# Ступень 2: удаление. Метки удаления + фильтр после поиска: сколько остаётся в выдаче; и BM25 со старой статистикой.
from ulib import *
ids, texts, queries, qs, D, Q, rels = setup()
allrel = set().union(*rels); nonrel = np.array([i for i in range(len(ids)) if i not in allrel])
S = Q @ D.T
print(f"статей всего {len(ids)}, из них правильных хоть для одного вопроса {len(allrel)}; удаляем только остальные")
for frac in (0.1, 0.3, 0.5, 0.7):
    rng = np.random.default_rng(0); dead = np.zeros(len(ids), bool)
    dead[rng.choice(nonrel, int(frac * len(ids)), replace=False)] = True
    row = []
    for fetch in (10, 20, 40):
        top = np.argsort(-S, axis=1)[:, :fetch]
        kept = [[i for i in t if not dead[i]][:10] for t in top]
        cnt = np.array([len(k) for k in kept])
        row.append(f"берём {fetch}: в среднем {cnt.mean():.1f} из 10, неполных {int((cnt < 10).sum())}/300")
    print(f"удалено {int(frac*100)}%: " + "; ".join(row))
# Правильный путь: фильтр внутри поиска (удалённым ставим минус бесконечность до выбора десятки)
rng = np.random.default_rng(0); dead = np.zeros(len(ids), bool); dead[rng.choice(nonrel, int(0.5 * len(ids)), replace=False)] = True
S2 = S.copy(); S2[:, dead] = -np.inf
print(f"фильтр внутри поиска при 50%: неполных выдач {int((np.isfinite(np.sort(S2, axis=1)[:, -10:]).sum(1) < 10).sum())}/300")
# BM25: удалённые остаются в статистике (df, N, средняя длина) против пересборки без них
docs = [terms(t) for t in texts]; qterms = [terms(queries[q]) for q in qs]
alive = np.where(~dead)[0]; pos = {int(i): j for j, i in enumerate(alive)}
rels_alive = [{pos[i] for i in r} for r in rels]
idx_docs = [docs[i] for i in alive]
stale = StatBM25(idx_docs, stats_docs=docs); fresh = StatBM25(idx_docs)
f = lambda bm: ndcg_rows(np.stack([bm.scores(q) for q in qterms]), rels_alive)
print(f"BM25 после удаления 50%: статистика со старыми статьями {f(stale):.3f}, пересчитанная {f(fresh):.3f}")

Что видно. Без запаса при 10% удалённых неполной оказалась 180 выдач из 300, при 50% — все 300, в среднем 5,5 результата вместо 10. Запас 20 держит до 30% удалённых (одна неполная выдача из 300), запас 40 — до 50%, а при 70% даже он оставляет 54 неполные выдачи. Фильтр внутри поиска даёт ноль неполных при 50%. Со статистикой BM25 на нашем испытании вреда нет: со старыми статьями 0,723, после пересчёта 0,716, то есть даже чуть выше. Удаляли случайные статьи, частоты слов от этого почти не сдвинулись. Если удалить целую тему, картина может быть другой, и проверять это нужно на своём случае.

Где обычно ошибаются.

  • Ставят фильтр «не удалено» после поиска с k ровно 10 и не мерят, сколько результатов реально доходит до пользователя или модели.
  • Выбирают запас один раз и забывают: удалённых со временем становится больше, и запас, достаточный при 10%, проваливается при 50%. Уборку индекса надо запускать по доле меток, а не «когда-нибудь».
  • Удаляют статью из основной базы, но не из кэша ответов или из уже собранного контекста. Удалённый текст продолжает всплывать через другую дверь.

Словарь ступени.

Метка удаления (tombstone). Отметка, что запись удалена, при том что сама запись ещё лежит в индексе.

Уборка (compaction). Пересборка сегментов индекса, при которой помеченные записи выбрасываются по-настоящему.

Фильтр после поиска (post-filter). Сначала выбрать k лучших, потом выкинуть неподходящие; выдача может стать короче k.

Фильтр внутри поиска (pre-filter). Неподходящие исключаются до выбора лучших; выдача остаётся полной.

Запас кандидатов (over-fetch). Брать больше кандидатов, чем нужно показать, чтобы после фильтра хватило.

Неполная выдача. Выдача, где после фильтра осталось меньше результатов, чем просили.

Жёсткое удаление (hard delete). Физическое удаление записи из индекса и хранилища, а не пометка.

3 Новая версия документа: замена по идентификатору и дубли в выдаче

Зачем это в работе. Документы правят: дописывают раздел, исправляют цифры, загрузчик сначала забирает заголовок, а позже полный текст. Если новую версию просто дописать в индекс, старая никуда не денется. Тогда в выдаче одна и та же статья займёт два места, а модель получит две версии текста, одна из которых устарела, и может опереться именно на неё. Нужна операция «заменить запись с этим идентификатором», и её надо проверять.

Как это устроено. У каждого документа должен быть устойчивый идентификатор (id) — имя, которое не меняется от версии к версии: номер статьи, путь к файлу, адрес страницы. Операция вставки-или-замены (upsert) кладёт запись с этим id, а если запись уже есть, заменяет её. Многие векторные базы так делают, если вы передали тот же id. Если же id каждый раз новый (например, случайный или посчитанный от текста), upsert превращается в обычную вставку.

Если документ режется на куски, у одной статьи несколько записей. Тогда новая версия может дать другое число кусков: было пять, стало три. Замена по id кусков оставит два старых куска висеть. Надёжнее хранить у каждого куска id родительского документа и при обновлении сначала удалять все куски этого родителя, потом вставлять новые.

Второй рубеж защиты — склейка по id на выходе (dedup): после поиска оставлять из каждого документа только лучший результат. Она убирает дубли из выдачи, но не решает главного: в индексе по-прежнему лежит устаревший текст, и если именно он оказался ближе к вопросу, модель получит его.

Чем это отличается от удаления: при удалении записи не должно быть вовсе, при обновлении должна быть ровно одна, самая свежая.

Пример. «Старая версия» статьи — только её заголовок, «новая» — заголовок плюс аннотация. Векторы заголовков у нас уже посчитаны в дорожке от 23.11. Обновляем 20%, 50% и 100% статей, но старые записи не удаляем: в индексе лежат и новые, и старые, у каждой записи помечено, чья она. Смотрим, сколько мест в первой десятке занимают повторы, и что даёт склейка по id.

Где обычно ошибаются.

  • Генерируют id записи случайно или от содержимого текста. Тогда каждая правка создаёт новую запись, и замена по id ничего не заменяет.
  • Обновляют куски документа по их собственным id и оставляют «лишние» старые куски, когда новых стало меньше.
  • Лечат дубли склейкой на выходе и считают задачу решённой. Выдача выглядит чистой, но в контекст по-прежнему может попасть устаревший текст.

Словарь ступени.

Устойчивый идентификатор. Имя документа, которое не меняется при правках текста.

Вставка-или-замена (upsert). Записать документ под его id: если такой уже есть, заменить, если нет — добавить.

Родительский документ. Целая статья, к которой относятся её куски; у каждого куска хранится id родителя.

Склейка по id (dedup). Оставить в выдаче один, лучший, результат от каждого документа.

Устаревшая копия. Прежняя версия документа, которая осталась в индексе после правки.

Версия документа. Номер или время правки, по которым понятно, какая запись свежее.

Повтор в выдаче. Место в первой десятке, занятое второй записью того же документа.

4 Сменили модель или обработку: почему векторы двух версий нельзя смешивать

Зачем это в работе. Рано или поздно вы захотите модель векторов получше или поменяете подготовку текста: другую длину обрезки, другой способ получить вектор из скрытых состояний, нормировку. Пересчитать миллионы статей быстро нельзя, и возникает соблазн пересчитывать по частям, а новые статьи сразу кодировать новым способом. Это самая тихая поломка поиска: размерность векторов совпадает, база не выдаёт ни одной ошибки, а качество падает в разы.

Как это устроено. Вектор имеет смысл только относительно других векторов той же модели и того же способа обработки. Модель расставляет тексты в пространстве (наборе координат) так, что близкие по смыслу оказываются рядом. Другая модель расставляет их по-своему: координата номер 17 у неё означает что-то другое. Косинус между вектором из одного пространства и вектором из другого — просто число, не мера смысла.

Даже одна и та же модель даёт разные пространства при разной обработке. Наша модель MiniLM выдаёт по вектору на каждый токен; итоговый вектор текста мы получаем средним по токенам (mean pooling). Можно вместо этого взять вектор служебного токена [CLS], который стоит первым (CLS pooling). Модель обучали со средним, поэтому векторы [CLS] у неё устроены иначе: они все довольно похожи друг на друга. Ещё одна частая разница — нормировка: если векторы не приведены к длине 1, скалярное произведение (сумма попарных произведений координат) начинает поощрять длинные векторы, а не близкие по направлению.

Смешанный индекс ломается сильнее, чем каждый способ по отдельности. Близости «вопрос старым способом — статья старым способом» и «вопрос старым способом — статья новым способом» лежат в разных диапазонах. Поэтому в первую десятку попадают статьи только той версии, чей диапазон выше, а вторая половина базы становится невидимой, какой бы правильной она ни была.

Отличие от ступени 1: там модель та же и векторы старых статей остаются верными. Здесь старые векторы становятся несовместимы с новыми вопросами, и пересчитать нужно всё — и статьи, и вопросы — одним способом.

Пример. Посчитали векторы всех статей и вопросов той же моделью, но двумя новыми способами: вектор [CLS] вместо среднего и среднее без нормировки. Затем изображаем пересчёт по частям: 30% и 50% статей в индексе уже «новые», остальные «старые», а вопросы кодируются то старым, то новым способом.

import time, numpy as np
from lib import *
ids, texts, queries, qt, _ = load_all(); qs = sorted(qt)
bi = BiEncoder()
def enc_all(tx, batch=64):
    cls, raw = [], []
    for s in range(0, len(tx), batch):
        enc = bi.tok.encode_batch(tx[s:s+batch])
        ids_ = np.array([e.ids for e in enc], dtype=np.int64); m = np.array([e.attention_mask for e in enc], dtype=np.int64)
        h = bi.sess.run(None, {"input_ids": ids_, "attention_mask": m, "token_type_ids": np.zeros_like(ids_)})[0]
        c = h[:, 0]; cls.append(c / np.linalg.norm(c, axis=1, keepdims=True))
        raw.append((h * m[..., None]).sum(1) / m.sum(1, keepdims=True))
    return np.concatenate(cls).astype(np.float32), np.concatenate(raw).astype(np.float32)
t = time.time()
Qc, Qr = enc_all([queries[q] for q in qs]); np.save("Q_cls.npy", Qc); np.save("Q_raw.npy", Qr)
Dc, Dr = enc_all(texts); np.save("D_cls.npy", Dc); np.save("D_raw.npy", Dr)
print("done", round(time.time() - t), "s")

  • Проверяют совместимость по размерности. 384 = 384 ничего не говорит: у нас три несовместимых способа, и все дают 384 числа.
  • Пересчитывают базу по частям «на ходу» в том же индексе. Пока пересчёт идёт, поиск отдаёт перекошенные результаты, и никакая ошибка об этом не сообщает.

Словарь ступени.

Пространство векторов. Расстановка текстов по координатам, которую задаёт конкретная модель с конкретной обработкой; сравнивать можно только векторы одного пространства.

Усреднение по токенам (mean pooling). Вектор текста как среднее векторов всех его токенов.

Вектор [CLS] (CLS pooling). Вектор текста как вектор первого служебного токена; годится, если модель так обучали.

Нормировка. Деление вектора на его длину, чтобы длина стала 1 и скалярное произведение совпало с косинусом.

Скалярное произведение (dot product). Сумма попарных произведений координат двух векторов; зависит и от угла, и от длины.

Смешанный индекс. Индекс, где часть векторов посчитана одним способом, часть — другим.

Конвейер векторов (embedding pipeline). Всё, что делает из текста вектор: подготовка, обрезка, модель, усреднение, нормировка.

5 Переиндексация без простоя: второй индекс, проверка и переключение

Зачем это в работе. Из ступени 4 следует: смену модели или обработки нельзя проводить в живом индексе. Нужен способ собрать новый индекс рядом, убедиться, что он не хуже, и переключить на него поиск одним движением, а при беде так же быстро вернуться. Плюс нужна регулярная проверка, что конвейер векторов не поменялся тихо — после обновления библиотеки, токенизатора или чужого кода.

Как это устроено. Схема «два индекса» (blue-green): рядом с рабочим индексом строится новый, в который пересчитываются все статьи новым конвейером. Поиск обращается не к индексу напрямую, а к псевдониму (alias) — имени, за которым стоит конкретный индекс. Пока новый не проверен, псевдоним указывает на старый. Переключение — смена одного указателя, откат — такая же смена обратно. Статьи, которые пришли во время пересчёта, пишутся в оба индекса или дописываются в новый перед переключением.

Рядом с индексом хранят паспорт (manifest): название модели и её версию, длину обрезки, способ усреднения, нормировку, приставки к тексту, размерность, дату сборки. При старте поиск сверяет паспорт с конвейером, которым он кодирует вопросы, и отказывается работать при расхождении. Это ловит ошибки, которые размерность не ловит.

Вторая проверка — сверка пересчётом. Раз в день или после каждого обновления зависимостей берут 200 случайных статей, заново кодируют их текущим конвейером и сравнивают с векторами в индексе. Тот же конвейер на процессоре даёт косинус практически 1. Если косинус заметно ниже, конвейер изменился, и вопросы кодируются не так, как статьи.

Третья — ворота качества перед переключением. Новый и старый индексы прогоняют по одному набору проверочных вопросов и смотрят не только среднюю метрику, но и разброс (бутстрэп — повторный подсчёт среднего на случайных выборках вопросов с повторением), число вопросов, которые стали лучше и хуже, сильные падения и долю совпадения первых десяток. Совпадение важно и само по себе: если изменились почти все десятки, пользователи заметят, даже при равной метрике.

Пример. Сначала сверка: 200 случайных статей (зерно 7) кодируем заново тем же конвейером и конвейером с [CLS] из ступени 4. Потом ворота для двух кандидатов на новый индекс, которые мы считали в дорожке от 23.11: с обрезкой текста до 512 токенов вместо 256 и до 64 токенов.

# Ступень 5: переиндексация с проверкой. Сверка пересчёта с сохранённым и ворота «старый индекс против нового».
from ulib import *
ids, texts, queries, qs, D, Q, rels = setup()
Dc = np.load("D_cls.npy")
rng = np.random.default_rng(7); smp = rng.choice(len(ids), 200, replace=False)
bi = BiEncoder(); fresh = bi.encode([texts[i] for i in smp])
c_ok = (fresh * D[smp]).sum(1); c_bad = (Dc[smp] * D[smp]).sum(1)
print(f"сверка 200 случайных статей: тот же конвейер — косинус с сохранённым min {c_ok.min():.6f}; конвейер с [CLS] — min {c_bad.min():.3f}, медиана {np.median(c_bad):.3f}, max {c_bad.max():.3f}")
def per_query(S):
    out = []
    for n, rel in enumerate(rels):
        o = np.argsort(-S[n])[:10]; out.append((ndcg_ids(o.tolist(), rel), set(o.tolist())))
    return out
old = per_query(Q @ D.T)
for name in ("V_full512", "V_full64"):
    N = np.load(f"/workspace/put-gen-1123/{name}.npy"); new = per_query(Q @ N.T)
    a = np.array([x[0] for x in old]); b = np.array([x[0] for x in new]); d = b - a
    ov = np.mean([len(x[1] & y[1]) / 10 for x, y in zip(old, new)])
    boots = [d[rng.integers(0, len(d), len(d))].mean() for _ in range(2000)]
    lo, hi = np.percentile(boots, [2.5, 97.5])
    print(f"{name}: nDCG@10 старый {a.mean():.3f}, новый {b.mean():.3f}, разница {d.mean():+.3f} (95% бутстрэп {lo:+.3f}…{hi:+.3f}); "
          f"лучше {int((d > 0).sum())}, хуже {int((d < 0).sum())}, без изменений {int((d == 0).sum())}; упали больше чем на 0,3: {int((d < -0.3).sum())}; "
          f"общая часть первых десяток {ov*100:.0f}%")

V_full512: nDCG@10 старый 0.648, новый 0.653, разница +0.004 (95% бутстрэп -0.009…+0.017); лучше 36, хуже 30, без изменений 234; упали больше чем на 0,3: 8; общая часть первых десяток 84%
V_full64: nDCG@10 старый 0.648, новый 0.575, разница -0.073 (95% бутстрэп -0.105…-0.040); лучше 47, хуже 81, без изменений 172; упали больше чем на 0,3: 52; общая часть первых десяток 58%

Что видно. Тот же конвейер даёт минимальный косинус 1,000000, конвейер с [CLS] — от 0,287 до 0,519: сверка ловит подмену сразу, по любым 200 статьям. Кандидат с обрезкой 512 по среднему чуть лучше (0,653 против 0,648), но интервал бутстрэпа от −0,009 до +0,017 захватывает ноль: улучшение не доказано. При этом 8 вопросов упали больше чем на 0,3, а 16% первых десяток изменились — повод посмотреть эти вопросы глазами, прежде чем переключать. Кандидат с обрезкой 64 провалил бы ворота: −0,073, интервал целиком ниже нуля, 52 сильных падения, совпадение десяток только 58%.

Где обычно ошибаются.

  • Пересобирают индекс «на месте», удалив старый, и теряют возможность отката. Если новый окажется хуже, вернуть прежний поиск можно только новым долгим пересчётом.
  • Смотрят только на среднее. Равное среднее может прятать десятки вопросов, которые резко упали, и почти полностью другие выдачи.
  • Не хранят паспорт индекса. Через полгода никто не помнит, какой обрезкой и какой версией модели он собран, и сверить конвейер вопросов не с чем.

Словарь ступени.

Два индекса (blue-green). Новый индекс строится рядом с рабочим, и поиск переключают на него только после проверки.

Псевдоним индекса (alias). Имя, через которое поиск обращается к индексу; переключение — смена того, на что оно указывает.

Паспорт индекса (manifest). Запись о том, какой моделью и какой обработкой собран индекс.

Сверка пересчётом. Заново закодировать выборку статей и сравнить с векторами в индексе, чтобы поймать тихую смену конвейера.

Ворота качества. Набор проверок, которые новый индекс обязан пройти перед переключением.

Бутстрэп. Оценка разброса метрики: много раз пересчитать среднее на случайной выборке вопросов с повторением.

Совпадение первых десяток. Доля результатов первой десятки, общих у старого и нового индекса.

Откат (rollback). Возврат поиска на прежний индекс, если с новым что-то не так.
